# Orby 1.4.1 — اصلاح قابلیت تکرار دمو

نسخهٔ فعال این دستگاه در `C:\Projects\Orby` است. فایل‌های start/stop پوشهٔ قدیمی IDE به همین نصب هدایت می‌شوند. در Settings، بخش Installation readiness نسخهٔ بک‌اند، وضعیت واقعی مدل، شبکهٔ RPC سرور و کیف‌پول، قرارداد و اقدام لازم برای رفع اتصال را نشان می‌دهد. یک clone بدون `.env` عمداً کلید خصوصی یا قرارداد مالک را همراه ندارد؛ تنظیم‌نبودن آن به معنی اتصال موفق نیست.

[ویدئوی پیوستهٔ اجرای کامل، ۷:۲۴ دقیقه](demo-1.4.1/real-mission-45919c01-007b-4309-8872-b9e1d235e47d.webm) · [گزارش واقعی مدل/تست‌نت و ۱۷ تراکنش](orby-real-mission-1.4.1.json). سناریو شامل شکست و بازیابی متخصص، اصلاح واقعی Recommendation، رد تأیید نسخهٔ قدیمی و تسویهٔ نسخهٔ ۱ است. ۱۰۸ تست خودکار، بیلد هر دو بخش و بازیابی بکاپ پاس شده‌اند.

## نصب و اجرای یک‌جا

پیش‌نیاز: Git و Node.js 24 همراه npm؛ Node 22.19 نیز پشتیبانی می‌شود. از پوشهٔ backend:

```powershell
npm run local
```

PostgreSQL، migrationها، API، worker، Angular و مدل محلیِ پیکربندی‌شده با همان launcher بالا می‌آیند. آدرس پیش‌فرض `http://127.0.0.1:4200` است. توقف: `Ctrl+C` یا `npm run local:stop`.

برای نصب مدل واقعی روی Windows x64، برنامه متوقف شود، سپس:

```powershell
npm run demo:model:setup
npm run local
```

مدل این دستگاه Qwen2.5-1.5B-Instruct-Q4_K_M با llama.cpp b12375 است. دانلود اولیه حدود ۱٫۱۲ گیگابایت است و SHA-256 بررسی می‌شود. API محلی هزینهٔ صورتحساب ندارد؛ برق، سخت‌افزار و gas کاملاً قیمت‌گذاری نشده‌اند و مانده «سود» نامیده نمی‌شود. نصب خودکار مدل روی Linux/macOS در این تحویل آزمایش نشده است. `.env.example` بدون secret است؛ کلیدهای تست‌نت و فایل حساب‌های توسعه در Git قرار ندارند.

## تست «انجام بده → نتیجه را ببین»

۱. Settings → Recheck connections: مدل باید `READY` و اتصال تست‌نت باید `CONNECTED` باشد. بررسی شبکه با پاسخ `status` انجام می‌شود؛ وجود کد قرارداد و نسخهٔ ۳ نیز کنترل می‌شوند. RPC اشتباه، قرارداد غایب و نبود تنظیمات، پیام‌های جدا دارند. در نصب بدون تنظیمات مالک، ابتدا علت و اقدام لازم نمایش داده می‌شود.

۲. Create a job → Draft an agreement from your goal: یک هدف دربارهٔ بازاریابی و هدف دیگری دربارهٔ مشخصات محصول وارد شود. عنوان، brief و حدود کلمات/الزام استناد پیشنهادی باید متفاوت و قابل ویرایش باشند. دکمهٔ غیرفعال علت دارد و Recheck model connection آمادگی واقعی را دوباره می‌سنجد. پیشنهاد توافق، انتشار یا پرداخت انجام نمی‌دهد. [خروجی دو درخواست واقعی و انتخاب دو متخصص متفاوت](orby-ai-planning-1.4.1.json).

۳. مدل قطع شود → دکمه/فرم علت نبود اتصال را نشان می‌دهد و API خطای مشخص برمی‌گرداند؛ خروجی ثابت با برچسب AI تحویل داده نمی‌شود. [اثبات خاموش‌کردن واقعی فرایند مدل و ثابت‌ماندن موجودی](orby-model-outage-1.4.1.json). پس از این تست launcher مجدداً اجرا شده است.

۴. Balance → Ethereum / USDC → مبلغ ۱۰، مقصد wNEAR، گیرندهٔ نمونهٔ ۶۴ کاراکتری hex و refund معتبر EVM: باید quote واقعی با دریافتی تخمینی، حداقل دریافتی و انقضا دیده شود. [نتیجهٔ واقعی](orby-intents-safe-mode-1.4.1.json). آدرس‌های نمونه در این تست صرفاً برای پیش‌نمایش هستند.

تبدیل decimals در بک‌اند نیز انجام می‌شود: ۱۰ USDC با precision=6 برابر 10000000 واحد است. `dry:true` در درخواست خروجی بک‌اند تعیین می‌شود؛ `dry:false` و فیلدهای اجرایی رد می‌شوند. امضا، آدرس واریز اجرایی، انتقال یا credit موجودی وجود ندارد. فقط شبکه‌های EVM پشتیبانی‌شده و NEAR در این فرم ارائه می‌شوند.

مبلغ صفر/منفی، دقت اضافی و آدرس نامعتبر باید قابل اصلاح باشند. نبود مسیر، حداقل مبلغ، محدودیت نرخ، timeout، قطع ارتباط و پاسخ غیرقابل‌خواندن سرویس، کد/پیام جدا دارند. فرم در شکست token discovery از ابتدا غیرفعال و دارای علت/Retry است. تغییر ورودی، quote قبلی و پاسخ دیررس ورودی قبلی را نامعتبر می‌کند؛ quote منقضی حذف می‌شود.

علت قابل اثبات در کد قدیمی: exceptionهای `fetch` و parse پاسخ غیر JSON بدون تبدیل به خطای دامنه به handler عمومی ۵۰۰ می‌رسیدند؛ اعتبارسنجی آدرس نیز فقط پسوند تست‌نت را رد می‌کرد. برای خطای تاریخی مرورگر، request-id و لاگ همان لحظه ارائه نشده بود؛ علت تاریخی قطعی اختراع نشده است. درخواست معتبر اکنون با سرویس واقعی پاس شده و خطاهای سرویس با fixture اعلام‌شده جدا آزمایش می‌شوند. لاگ جدید فقط کد طبقه‌بندی‌شده و وضعیت را ثبت می‌کند و پاسخ خام حساس به فرم برنمی‌گردد.

۵. یک کار تازه با مدل واقعی و Agent-managed mission منتشر شود → برنامه و سقف escrow مشتری و هزینهٔ متخصص از موجودی سازنده دیده شوند → برنامه تأیید شود → امضای تأمین وجه انجام شود. درخواست مربوط به شواهد باید متخصص شواهد و درخواست بررسی ساختار باید متخصص قالب را انتخاب کند؛ مدل از فهرست مجاز انتخاب می‌کند و قیمت را سرور تعیین می‌کند.

۶. در دمو گزینهٔ کنترل‌شدهٔ شکست تلاش اول فعال شود → اولین خروجی واقعی متخصص در چک پذیرش رد شود → فقط یک اصلاح انجام شود → همان escrow مجدداً استفاده شود. Live collaboration خلاصه و بازشونده است؛ وضعیت، تعداد تلاش، چک‌ها و هزینهٔ API هر تلاش قابل بررسی‌اند. شکست دوم کار را برای تصمیم کاربر متوقف می‌کند؛ پرداخت یا استخدام موفق قبلی دوباره شارژ نمی‌شود.

۷. پس از تحویل، روی Request a change to this recommendation کلیک و دقیقاً `Start Recommendation with Audit revision:` وارد شود → نسخهٔ ۱ باید واقعاً با `Audit revision:` شروع شود، ردیف‌های دیگر حفظ شوند، نسخهٔ صفر باقی بماند و چک‌ها دوباره اجرا شوند. تأیید نسخه/هش صفر باید `DELIVERY_CHANGED` بدهد. در Simulation، دستور prefix و توضیح شواهد هدفمند پشتیبانی می‌شوند؛ بازنویسی آزادِ پشتیبانی‌نشده پیش از مصرف فرصت اصلاح رد می‌شود. در مدل واقعی، درخواست، بخش هدف، چک‌ها و خروجی قبلی به runtime می‌رسند.

در آزمون واقعی، لاگ llama.cpp نشان داد escape عبارت منظم `\S` پشتیبانی نمی‌شد و قید به «هر رشته» تبدیل می‌شد. قید سازگار `[^ ]` جایگزین شد و بررسی مستقل نتیجه نیز اضافه شد: مدلِ بی‌اعتنا به prefix، `MODEL_REVISION_NOT_APPLIED` می‌گیرد و نتیجهٔ موفق جایگزین نمی‌شود. این یک محدودیت واقعی در زیرمجموعهٔ JSON Schema/grammar این runtime بود؛ [مستندات اصلی grammar](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md). [آزمون واقعی مدل پس از اصلاح](orby-real-revision-preflight-1.4.1.json). اجرای ردشده با [اختلاف، award صفر و بازپرداخت کامل escrow اصلی](orby-revision-regression-refund-1.4.1.json) بسته شد؛ خروجی قبلی یا سابقهٔ پذیرش بازنویسی نشد.

۸. Review settlement → مبلغ، کارمزد، سهم سازنده و بازپرداخت دیده شوند → کاربر نسخهٔ فعلی را امضا کند → receipt و لینک تراکنش‌های نهایی نمایش داده شوند. هش یا بسته‌شدن پنجرهٔ کیف‌پول به‌تنهایی موفقیت نیست؛ final RPC و receiptهای زنجیره کنترل می‌شوند. عملیات نامشخص ابتدا reconcile می‌شود. در Simulation، پیام پایان و رسید از پرداخت/لینک واقعی زنجیره ادعا نمی‌کنند.

## داده‌های نمایشی تکرارپذیر

در حالی که دیتابیس launcher فعال است، از backend:

```powershell
npm run demo:seed:samples
```

Settings → Switch demo account → Demo / Sample workspace → Enter simulation: پانزده کار نمونه در سه موضوع، با حالت‌های باز، تأمین‌شده، اجرا، بررسی، تحویل اصلاح‌شده، تسویه، لغو، بازپرداخت، چک ناموفق، timeout/بازیابی و توقف دیده می‌شوند. دو Knowledge، دو Template و یک Program متوقف‌شده وجود دارند. هیچ زمان‌بندی نمونه به‌صورت پیش‌فرض فعال نیست.

همهٔ این‌ها snapshot ساختگی و برچسب‌خورده‌اند، در حساب `samples.demo` قرار دارند، وارد آمار موفقیت واقعی ایجنت نمی‌شوند و هش تراکنش جعلی یا ادعای مدل واقعی ندارند. صورت‌حساب‌ها با منطق موجود Simulation ساخته می‌شوند؛ انتقال‌ها به همان job متصل و ledger متوازن است. اجرای مجدد داده تکراری نمی‌سازد و دادهٔ کاربر را پاک نمی‌کند. نمونه‌ها برای اجرای زنده باید Copy شوند؛ نمونهٔ ثابت پرداخت/اجرای مجدد نمی‌گیرد. تست و ویدئوی واقعی با کار تازه از ابتدا اجرا می‌شوند.
