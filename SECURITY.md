# Runtime security boundaries

Version 1.3 adds indexed V3 contract storage, independent sponsor accounting, reserved exit capacity, exact-version native approval, per-stage knowledge grants and live workspace membership enforcement. See `docs/REVIEW_V2_RELEASE.md` and `docs/DEPENDENCY_REVIEW.md` for verification boundaries.

The same-origin production server applies CSP to all routes and rewrites every SPA document with a random per-response script nonce. Inline handlers, eval, objects and framing by other sites are blocked. HTML is not cached. Angular receives ngCspNonce; the wallet connector receives the same nonce for its sandboxed adapter scripts. Wallet popups use same-origin-allow-popups.

The paired Angular production build disables inline critical CSS. This prevents the optimizer from generating print-only stylesheets with inline onload handlers that CSP correctly blocks. The full minified stylesheet loads as an ordinary stylesheet before rendering.

Wallet registry/adapters require HTTPS connections and images from varying providers. connect-src permits HTTPS/WSS, frame-src permits HTTPS and styles permit unsafe-inline for the wallet SDK. These are deliberate compatibility allowances, not a fully locked-down third-party supply chain. Script execution in the application remains limited to same-origin scripts and nonce-authorized code. The SDK runs downloaded wallet adapters in an opaque-origin sandbox. Public wallet RPC is configured separately with NEAR_WALLET_RPC_URL; server-side NEAR_RPC_URL is not exposed to browsers.

NEP-413 challenges bind a one-use random nonce, message, recipient/host, expiry and declared flow. DIRECT verification requires the configured same-origin callback in the digest. Only a challenge created for REDIRECT can use the redirect compatibility path, which accepts the expected callback or its omission. The frontend uses that path when consuming a signature returned in the URL fragment; normal returned signatures use DIRECT verification. Flow selection alone never proves wallet ownership: a valid signature and a FullAccess key registered to that testnet account remain mandatory. A signature with another callback is not accepted. Demo login uses accountId; account remains a compatibility alias.

Pending agent recovery is owner-only, checks the contract, compares manifest hashes, and never issues a second registration while a known transaction is UNKNOWN or SUBMITTED. PREPARED recovery reuses the same operation/request ID. A new operation is allowed after a definitive FAILED result and absence of the agent on the contract. Recovery cannot discard an uncertain payment or registration.

Uploads are private by default. Every owner has a shared limit across both books: 100 files, 50 MiB decoded content, and 25 unused files. Transaction advisory locks serialize quota checks and inserts across different idempotency keys. Attached files count toward storage; they cannot be deleted through the unused-upload endpoint. Public IPFS publishing still requires explicit consent.

Only testnet is supported. Mainnet, an independent security audit, production key custody and production monitoring are not covered by local verification.

## Workspace programs and integrations (1.2)

User transaction review precedes every wallet transaction. The reviewed signer must still match both the authenticated server session and the wallet account immediately before signing. Local pending operations, request keys and server history are scoped to the account, book and configured contract. An unverified candidate hash is stored separately; only a transaction with the exact expected signer, contract, method, arguments, gas and deposit can become the verified hash. Confirmation requires FINAL execution. Withdrawals also require the matching contract's successful withdrawal callback for that account and request ID. An unresolved result remains uncertain and must be reconciled without sending another payment. See [NEAR RPC finality](https://docs.near.org/api/rpc/transactions).

Explicit approvals and revision requests bind the delivery revision and hash. A dispute award does not manufacture a client approval. Historical decisions keep provenance. The upgraded contract preserves the v2 data layout and adds version-bound approval, one targeted revision and release of available bond; reserved performance collateral cannot be released. Simulation workers filter their book before leasing queue work.

Private knowledge, templates, programs and Google connections are account/book scoped. Knowledge is shared as an explicitly selected immutable job snapshot, subject to the job's access rules. Public profiles anonymize private job history; seeded examples do not inflate real completion counts. Knowledge, templates and programs have quotas. Program creation and launch are serialized. Milestones have independent job terms and wait for previous settlement. Paid trials have separate escrow and pay each successful participant. Pausing a program stops future runs, not existing signed obligations.

Recurring monthly ceilings are conservative workspace escrow reservations, not a global on-chain wallet allowance. Automatic funding requires explicit consent and is simulation-only. On testnet every program job must be published and funded through wallet review/signature. The scheduler cannot sign a client payment.

Google OAuth uses a one-use expiring state, browser-bound HttpOnly cookie, PKCE and server-side code exchange. Tokens are encrypted with AES-256-GCM using a separately protected key. Reading rows and writing output require the connected user's account and an explicit spreadsheet/range. A write requires a five-minute version-bound preview and confirmation. Appends use RAW values, preserve existing rows and include a unique reconciliation marker. Unknown writes are reconciled rather than automatically repeated. Live Google consent was not tested without owner-provided OAuth configuration; the integration tests use a declared HTTP fixture. Preserve the encryption key separately from database backups. Disconnect deletes local tokens; revoke Google's grant separately. See [integration setup](docs/GOOGLE_SHEETS_SETUP.md).

Drafts are stored in the current browser profile, separated by account/book. They can contain private text; use trusted devices. The deterministic demo only organizes provided evidence and does not independently verify claims. Optional model output never controls deterministic acceptance, authorizes payments or supplies executable instructions.
